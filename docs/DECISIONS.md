# Decisions

**Language:** ASD-STE100 Simplified Technical English, Issue 9. The technical names are
in §0 of [`TECHNICAL_DESIGN.md`](TECHNICAL_DESIGN.md).

Each row gives one decision and a short reason. The commit message gives the full
reason, and the conditions that make us examine the decision again.

| Date | Decision | The short reason | Commit |
|---|---|---|---|
| 2026-08-18 | A ticket is one directory with two files: `ticket.yaml` for the fields, and `ticket.md` for the prose. | The person writes the prose, and delegator writes the fields. Two files make the two owners clear, and no program must find the end of a header. | [611de08](https://github.com/alcubie/delegator/commit/611de08) |
| 2026-08-18 | Read and write YAML with `github.com/goccy/go-yaml`. | `gopkg.in/yaml.v3` was archived in April 2025. The v4 line of `go.yaml.in/yaml` is new, and its v1 to v3 lines are frozen. goccy has years of releases behind its API. | [5765188](https://github.com/alcubie/delegator/commit/5765188) |
| 2026-08-18 | Only `dg ticket` and `dg revise` write `ticket.md`. A command adds to the end of the file, and never writes it again from memory. | An append cannot lose text, because it does not hold the old text. A write from memory can put text that is minutes old over the text of the person. | [9d48c13](https://github.com/alcubie/delegator/commit/9d48c13) |
| 2026-08-18 | Write the limits on `result` and `flags` by hand. Do not use `github.com/go-playground/validator`. | Half of the rules of a ticket cannot be tags. A tag saves work only when a message for a developer is enough, and each message goes to an agent. The library adds 17 modules. | [91a1754](https://github.com/alcubie/delegator/commit/91a1754) |
| 2026-08-20 | Use hidden files for delegator-only files | Prefix with dot (.) for files that are only read by the program to further distinguish the files | [23f3ee](https://github.com/alcubie/delegator/commit/23f3ee) |
| 2026-08-24 | Keep the fields, the queue and the counter in one SQLite database. Keep the prose of each ticket in a file. | Lesson 3 came from the absence of a migration, and not from the database. `PRAGMA user_version` answers it. The database removes the project key, `project.toml`, `.queue`, `.next-id`, `.lock`, `ticket.yaml` and the write with a temporary file. The prose stays a file, because `$EDITOR` opens a file and not a row. | [e449033](https://github.com/alcubie/delegator/commit/e449033) |
| 2026-08-24 | Read and write SQLite with `modernc.org/sqlite`. | It is a translation of SQLite into Go, so it needs no cgo. A build with cgo needs a C compiler for each target of goreleaser, and `CGO_ENABLED=0` gives one static binary for Linux and macOS. |  |
| 2026-08-25 | **Light decision.** Use `database/sql` and write the SQL. Do not use an ORM now. | Two tables and about eight statements do not pay for an ORM. `PRAGMA user_version` gives the migration, and lesson 3 says that an automatic migration is the risk. Examine this decision again if the scan of a row into a structure becomes tedious. `github.com/jmoiron/sqlx` adds that scan and keeps the SQL. An ORM that controls the migration is the one choice here that is difficult to leave after a person installs delegator. |  |
| 2026-08-28 | Build the CLI with `github.com/spf13/cobra`. | Man pages are wanted, and `cobra/doc` makes them from the same command tree that gives `dg help` and the completion of each shell. A man page by hand is the same text in a second place, and the two come apart. The binary takes cobra and pflag only: `go-md2man` goes to a program that makes the documentation at a release, and not to `dg`. |  |
| 2026-08-28 | The inbox shows a mark for `flags`, and not the words. | Section 6.4 gives `flags` 240 characters, and one of those wraps a row of a terminal three times, so the inbox stops being a list that a person can read down. Section 9.1 asks the inbox to show which tickets have a problem, and a mark answers that. `dg show` gives the words. |  |
| 2026-08-28 | `dg revise` takes away the `result` and the `flags`. | The two are the report of the run that is complete. The person read them, and gives the work again because of what they said, so the next run writes its own. A ticket that waits therefore holds no report of an earlier run, and each group of the inbox can take the mark: a mark below QUEUED says that something is wrong now. |  |
| 2026-08-31 | The slug of a branch has ASCII characters only, and `github.com/gosimple/slug` makes it. | Git keeps the name of a branch as bytes and gives it no encoding. macOS keeps a name in one form and Linux keeps it in a different form, so one branch becomes two after a copy between them. A character of four bytes also uses four of the 255 bytes of a reference. The library gives the nearest ASCII form, and it cuts the slug at the end of a word, which a cut at 40 bytes does not do. It adds two modules, and the table of characters is 940 kB. This replaces the condition of ticket 4 that kept a character of more than one byte whole. |  |
| 2026-08-31 | The seam reads a session id back from a finished run with `SessionID`. It does not only give one to the agent. | Of the agents examined, only claude accepts an id at its start, with `--session-id`. The agents codex, gemini and opencode each make their own id and let a caller resume by it after the run, and gemini does not give the id in its output for a run with no terminal. Section 6.6 said that no code reads the output of an agent, and that is true of claude alone. The method costs one file now, because no adapter is written yet. It costs the supervisor and the claude adapter after ticket 11 and ticket 15. |  |
| 2026-09-01 | The agent reads a ticket with `dg show`, the same command as the person. There is no `dg read`. | Two commands that read one ticket can say different things, and the person examines the work through `dg show`. The two had already come apart in the design: `dg read` gave the prose alone, and the title is a column and not the first line of the prose, so the agent could not see the line that says what to do. The text of `dg show` needs no change for an agent, and the indent of two spaces does not stop one from reading it. Ticket 12 is cancelled. |  |
| 2026-09-01 | A run ends with one commit, and the ticket keeps its hash. There is no `result` and no `flags`, and the inbox has no mark. | The commit message is the report, and a `result` beside it says the same thing twice. The mark was worse than redundant: it came from the agent, about the work of the agent, so a ticket with no mark read as work that needs no examination, and an agent that is confidently wrong writes no flag. A run that changes nothing commits with `--allow-empty` and gives the reason there, so every run makes exactly one commit and `dg accept` never meets a worktree it cannot remove. This replaces the two rows of 2026-08-28 about the mark and about `dg revise`. |  |
| 2026-09-01 | Delegator never supplies a session id. Every adapter reads the id back from the output of its run. | Claude takes an id at its start with `--session-id`, and codex, gemini and opencode do not. An adapter that can be given one and three that cannot is two paths through the seam, and the first draft of that seam fitted claude alone. `claude -p --output-format json` gives `session_id`, so claude answers the same question as the others. The cost is that a run which stops before it reports an id has no session at all, and that cost is now the same for each agent instead of falling on three of four. |  |
| 2026-09-03 | A run is a row of the table `runs`, which holds the process id, the start time, the end time and the exit code. | Section 6.1 says that a run is a first class entity, and a ticket has more than one run after `dg restart` and `dg revise`. A column on `tickets` holds the last run only, and moves to a table later, which is a second migration and rework in each command that reads it. See §7 of [`RUN_CONTROL.md`](RUN_CONTROL.md). |  |
| 2026-09-03 | The supervisor claims its own ticket. `dg run` with no id reads the first ticket with room, claims it, and writes its process id, in one transaction. `Next` claims nothing. | A claim in the trigger leaves a start window in which the database says `running` and no program exists, so each check of a live supervisor needs a grace period. A claim in the supervisor removes the window, answers the open question of ticket 21, and makes more than one run at a time a count of free slots. See §5 of [`RUN_CONTROL.md`](RUN_CONTROL.md). |  |
| 2026-09-03 | A supervisor is alive if signal 0 finds its process id, the start time of its run is after the boot time, and the run is not older than the timeout. There is no file lock, and no check of the name of the program. | `dg cancel` needs the process id in each case, so the check adds no second mechanism. The boot time closes the case of a restart of the computer, where each old process id is free and the next `dg` command can get one. A file lock is correct in each case, but it is a second mechanism beside the first, and two can disagree. It stays in reserve. See §4 of [`RUN_CONTROL.md`](RUN_CONTROL.md). |  |
| 2026-09-04 | **Light decision.** Read the config file with `github.com/BurntSushi/toml`, and not with `github.com/pelletier/go-toml/v2`. | The two are equal on the conditions of ticket 24: each has no dependency of its own, each refuses a key that delegator does not know, each names the key of a value of the wrong type, and each had a release in the last year. The differences are in the errors. go-toml gives the line of the file with a mark below the bad value, and it lists every unknown key at one time, so a person corrects a file in one pass. BurntSushi gives one line with the key and the line number, and a list of the unknown keys that delegator formats itself. BurntSushi was chosen because `dg` writes one line for an error, and its one line for a wrong type names the TOML key, `runs`, where the one line of go-toml names the Go field, `Config.Runs`, and delegator would make its own line from the key. Its API is also one call, `DecodeFile`, and one list. Examine this decision again if an error about the config needs the excerpt of the file: go-toml gives it with no code, and BurntSushi gives it for a syntax error only. |  |
| 2026-09-10 | `dg cancel` keeps the worktree of the run it stopped. Only `dg accept` removes a worktree. | A run that a person stopped can hold work they want to read before it goes, and no removal can be undone. The branch keeps the commits either way, but the files that no commit holds are only in the worktree. `dg restart` also needs the worktree, because it continues the same run in the same one. The cost is a worktree on disk for each cancelled ticket, which a later command that clears them can take. §6.3 of [`TECHNICAL_DESIGN.md`](TECHNICAL_DESIGN.md) says the same. |  |
| 2026-09-11 | `dg edit` writes the file of prose again, with the text that its editor gave. This changes the row of 2026-08-18 for that one command. | The row of 2026-08-18 stops a write of text that is minutes old over the text of the person. The text here is the text that the person saw as the command ended, so there is no older text to lose. The command also writes no file when the editor gives the text back as it was. It refuses each ticket that the queue does not hold. |  |
| 2026-09-11 | A ticket in `ready` holds its slot. The limit `runs` counts the tickets in `running` and the tickets in `ready` together. | Ticket 22 asks for one supervisor for each free slot, and it also asks that a limit of 1 keeps the queue of today. A ticket in `ready` holds the queue today, so the two conditions agree only if a ticket in `ready` holds a slot. The limit is then the count of tickets that a run opened and the person did not close, and `dg accept` frees the slot. |  |
| 2026-09-11 | The continuation of a session is the command `dg chat <id>`, and not a command of the person in the config. | The example `claude --resume {session}` in §9.2 made the person the one who starts the agent. Typed by hand from the wrong directory on 2026-09-09, it made a new conversation and gave it the id of the old one, and nothing said so. Delegator knows more: the adapter of the run gives the argv with `Resume`, the worktree is the directory the conversation ran in, and the table `runs` says whether an agent is on that session now. `dg chat` refuses a ticket in `running` and names the process that holds it, so one conversation never gets two writers. |  |
| 2026-09-11 | The limit of one project is the key `max_runs_per_project` of the config, and it is the same for every project. The claim takes the first ticket of the queue whose project has room, and not always the first ticket of the queue. | Two runs of one project can use the same resource outside the worktree, such as a database or a port. The limit `runs` counts every project together and cannot stop that. The key names no project, so a person sets one value and gets it for each repository they add later; the cost is that a project that needs a different number cannot have one. A value of 0 is no limit for each project, so the file a person has today keeps the queue they have today. The condition is one more line in the `SELECT` that claims, so the claim stays one transaction. The second cost is that the first ticket of the queue is not always the next ticket to run: a ticket waits while a later ticket of a project with room starts, and the inbox gives no cause. | A project needs a limit that the other projects do not get. |
| 2026-09-14 | `RunSpec` carries a session, and `Launch` continues that conversation. For claude the argv is `claude -p --resume <id>`. | `dg restart` gives a failed ticket back to the queue. Section 6.3 says that the next run continues the same session, in the same worktree. The session must therefore go down through the seam, and the argv that continues it belongs to the adapter and not to the supervisor. This does not change the row of 2026-09-01: delegator still makes no id. The id in `RunSpec` is the id that the agent made and reported through `SessionID`. An empty session starts a new conversation, so an agent that cannot continue one needs no new field. |  |
| 2026-09-14 | The boot time on Windows is the time of the call, less the length that `windows.DurationSinceBoot` of `golang.org/x/sys` gives. That function is `GetTickCount64` of kernel32. | The reconcile compares the start of a run with the boot, so it needs a moment and not a length. `GetTickCount64` counts the milliseconds after the start of the computer, and it includes the time the computer was in sleep, as `btime` on Linux does. `QueryUnbiasedInterruptTime` leaves that time out, and the boot time from it is later than the boot. A run that started before a sleep then looks older than the boot, and the reconcile fails it. `golang.org/x/sys` is in `go.mod` already, and `DurationSinceBoot` is exported, so this file declares no syscall of its own. The cost is that a length and the clock together are not a moment the computer keeps. A change of the clock moves the value. |  |
| 2026-09-14 | `alive` on Windows opens the process with `OpenProcess` and `PROCESS_QUERY_LIMITED_INFORMATION`, and reads `GetExitCodeProcess`. A process with the code `STILL_ACTIVE` is alive. | Windows has no signal 0. The open alone is not the answer, because a handle that stays open holds the process of a program that ended, and `OpenProcess` opens that process. The exit code is the check that tells the two states one from the other. `PROCESS_QUERY_LIMITED_INFORMATION` is the least access that `GetExitCodeProcess` takes, and a process of another person gives it, where `PROCESS_QUERY_INFORMATION` does not. Only `ERROR_INVALID_PARAMETER` says that the process id is free, as only `ESRCH` says so on Unix. `golang.org/x/sys/windows` declares no `STILL_ACTIVE`, so the code reads `STATUS_PENDING`, which is the same number. The cost is that a program which ends with the code 259 reads as alive, and the timeout of the run covers it. |  |
